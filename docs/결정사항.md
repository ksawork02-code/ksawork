# 설계 결정 기록 (2026-11-07 ~ 11-08 Cowork 세션)

| 주제 | 결정 | 이유 |
|---|---|---|
| 플랫폼 | Google Apps Script 웹앱 + 구글 시트(DB) + 드라이브(파일) | 비용 0, 기관 구글 계정으로 운영, 별도 서버 불필요 |
| Lark 대체 방식 | 완전 이전 + 전환 기간 **Lark → 앱 단방향** 자동 동기화 | 양방향은 충돌 위험 큼. 필드 단위 병합: Lark에서 바뀐 칸만 반영, 같은 칸 충돌 시 Lark 우선(변경이력에 이전 값) |
| 로그인 | 이메일 6자리 OTP, 비밀번호 없음, 기기별 30일 토큰(스크립트 속성), 권한은 매 요청 시 시트 기준 재판정(10분 캐시) | gmail 계정은 웹앱에서 사용자 이메일을 알 수 없음. 컨설턴트 계정 = Lark 명단 이메일 |
| 웹앱 배포 | 실행: 나(USER_DEPLOYING), 액세스: 모든 사용자(익명) | 외부 기업 신청폼 + 컨설턴트가 시트 권한 없이 사용 |
| 메일 한도 | gmail 100명/일 → 마지막 15건은 로그인 코드용 예약(`MAIL_RESERVE`), 기한 알림은 컨설턴트별 1통으로 묶음 | Workspace 계정이면 1,500명/일 (권장) |
| 업로드 | 신청서·보고서는 `.hwpx`만, 전체 `.hwp` 차단, HWPX는 ZIP 매직바이트(PK) 검사 | 검수 자동화 스킬이 HWPX만 처리 |
| 파일 접근 | 드라이브 파일은 공유하지 않고 `downloadFile`이 권한 확인 후 base64 전달 | 사업자등록증 등 개인정보 보호 |
| 주소 | 넷리파이 정적 페이지가 웹앱을 iframe으로 감쌈(`/apply` `/pre` `/consultant` `/status` `/survey`), `PUBLIC_URL` 설정 시 메일 링크도 넷리파이 주소 | 앱스크립트 URL에 커스텀 도메인 불가 |
| 차수 일정 | 사업장별 날짜를 `차수일정` 시트로 분리, 생성 시 자동 입력, 일괄 적용 버튼 | Lark에서 같은 날짜를 사업장마다 반복 입력하던 문제 |
| 정산 | `수당기준` 표(항목·보고서·금액·분배) 금액이 있을 때만, 보고서 검수완료 시 정산 행 자동 생성(중복 방지) | 금액 규칙 미정 → 운영자가 입력 |
| 문자 | 솔라피 v4 API(HMAC-SHA256), 키는 스크립트 속성 | 알리고는 발송 IP 등록 필요(앱스크립트 IP 가변) |
| 요청 간 캐시 (2단계) | `all_()`이 시트 데이터를 `CacheService`에 30,000자 조각으로 10분 보관. 키에 시트별 버전(`v:시트`)을 넣고 `insert_/update_/remove_`·`onEdit`가 버전을 바꿈. 쓰기(락 안)는 항상 시트를 직접 읽음. `변경이력`·`메일이력`은 제외 | 요청마다 시트 여러 장을 읽는 비용 감소. 버전 키 방식이라 지울 키를 찾을 필요 없음. 행 삭제·정렬 같은 수동 변경은 onEdit가 못 잡으므로 최대 10분 지연 또는 메뉴 **앱 캐시 비우기** |
| 이력 보관 (2단계) | 매일 점검 때 `변경이력`·`메일이력`에서 `LOG_KEEP_MONTHS`(기본 3)개월보다 오래된 행을 `보관_변경이력_yyyy-MM` 시트로 이동(1회 최대 2만 행) | `historyOf_`는 최근 3,000행만 보므로 원본을 작게 유지 |
| 로그인 토큰 (2단계) | 한 사람당 최근 5개 토큰(기기)만 유지, 매일 점검에서 스크립트 속성 400KB 넘으면 관리자 메일 | 스크립트 속성 500KB 한도. 사파리처럼 매번 재로그인하는 경우에도 토큰이 무한히 쌓이지 않게 |
| 메일 한도 계산 (2단계) | 한도는 메일 수가 아니라 받는 사람 수(to+cc)로 계산. 일괄 메일은 예약분 15건을 뺀 한도로 사전 차단 | 관리자 여러 명에게 가는 알림이 1건으로 계산되던 오류 |
| 넷리파이 로그인 유지 (2단계) | 앱이 로그인 토큰을 `postMessage`로 래퍼(넷리파이, 1st-party)에 맡기고, iframe 저장소가 비어 있으면 시작할 때 돌려받음. 래퍼는 자기 iframe 안의 프레임에만 응답, 앱은 `PUBLIC_URL` 출처에만 보냄 | 사파리는 iframe(제3자) 저장소를 막거나 지움. 토큰을 URL에 넣지 않아 기록·리퍼러로 새지 않음. `PUBLIC_URL`이 비어 있으면 동작 안 함(기존과 같음) |
| 큰 첨부 (2단계) | 변경 없음. 이관 대상 최대 29MB, 업로드 한도 20MB → 40MB 초과(드라이브 URL 우회) 경로는 현재 데이터에 없음 | 실환경에서 29MB 파일 다운로드가 실패하면 조각 다운로드 검토 |
| 테스트 | Node 모의 Apps Script(`test/gas-mock.js`) + 실제 Lark 데이터 + Playwright UI | 앱스크립트 실환경 없이 로직·화면 검증 |

## 아직 실환경에서 검증하지 못한 것
- 실제 Apps Script 실행(권한 승인, 6분 제한, 트리거, LockService, CacheService 동작)
- 드라이브 실제 업로드/다운로드, 엑셀 내보내기(export URL + OAuth 토큰)
- 구글 캘린더 이벤트 생성, 솔라피 실제 발송
- 넷리파이 iframe 안에서의 localStorage(사파리 ITP) — 래퍼 토큰 보관으로 대응했으나 실기기 확인 필요(사파리는 7일간 방문 없으면 1st-party 저장소도 지울 수 있음), 회사 보안 프로그램 차단 여부
- 요청 간 캐시: 실제 응답 시간(사업장 상세·관리자 첫 화면 3초 목표), 단순 트리거 `onEdit`에서 CacheService 동작, 큰 시트의 조각 수
- 29MB 첨부 다운로드(`google.script.run` 응답 크기)
- 메일 실제 도달(스팸함)
